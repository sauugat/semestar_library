1. CURRENT AUTHENTICATION ARCHITECTURE RELEVANT TO TEACHERS
================================================================================
Semester Library operates a dual-auth architecture serving both Web and Mobile
clients, supported by a dual-engine database layer (Neon PostgreSQL in production
and LibSQL/SQLite in test environments).

A. Web Authentication:
   1. Client (public/auth.js) invokes POST /api/auth/login with identifier and password.
   2. Identifier may be username, studentId, or email.
   3. Server resolves identifier to email:
      SELECT email FROM students WHERE LOWER(username) = ? OR LOWER(studentId) = ?
   4. Server validates password against Supabase Auth:
      supabase.auth.signInWithPassword({ email, password })
   5. If valid and email is confirmed, server returns Supabase session JWTs:
      { access_token, refresh_token, expires_at }
   6. Web client stores session in localStorage and passes JWT via Bearer header:
      Authorization: Bearer <supabase_jwt>

B. Mobile Authentication:
   1. Client (mobile/context/AuthContext.tsx) invokes POST /api/mobile/login.
   2. Server resolves identifier to student record in students table.
   3. Server checks password via Supabase Auth first; falls back to bcrypt passwordHash
      for local/fixture accounts.
   4. Server generates an opaque 64-hex bearer token stored in mobile_tokens:
      INSERT INTO mobile_tokens (token, studentId, createdAt, expiresAt)
      (30-day token lifetime).
   5. Mobile client securely stores token via expo-secure-store and passes:
      Authorization: Bearer <opaque_token>

C. Unified Middleware (lib/auth-middleware.js):
   1. Distinguishes Supabase JWT (3 base64url segments separated by dots) from
      legacy 64-hex mobile tokens.
   2. Supabase JWT: Verifies token with Supabase Auth, maps user.id or email to
      students table row, synchronizes verification status if confirmed.
   3. Mobile Token: Validates against mobile_tokens table and checks expiration.
   4. Populates req.user and req.student with:
      - studentId, username, name, role, department, semester, gender, email,
        avatarUrl, verificationStatus
   5. Guards:
      - requireLogin: Validates presence of req.user.studentId.
      - requireAdmin: Validates req.user.role === 'admin'.

2. CURRENT ROLE MODEL & WHERE "TEACHER" FITS
================================================================================
The platform currently has 4 recognized roles:
1. 'student': Standard learner. Restricted to their single enrolled cohort (cohort_id).
2. 'cr': Class Representative. Learner with notice posting and moderation rights.
3. 'admin': Platform administrator. Institutional oversight and cohort management.
4. 'teacher': Faculty / Instructor.

FINDING: The 'teacher' role ALREADY EXISTS extensively in existing backend logic:
- lib/academic-context.js:
  role === 'teacher' || role === 'admin'
  -> canViewAllCohorts = true (Institutional oversight across all 4 cohorts)
  -> canManageCohorts = false (Teachers CANNOT manage or promote cohorts)
- routes/posts.js:
  -> Notices can be posted by: ['admin', 'cr', 'teacher']
  -> Assignments can be created by: ['admin', 'teacher']
- routes/code-lab/assignments.js:
  -> isStaff = role === 'admin' || role === 'teacher'
- routes/routine.js:
  -> Teachers can inspect routines across all cohorts.
- lib/cohort-chat.js:
  -> Staff filter: isStaff = role === 'teacher' || role === 'admin'
- lib/push-notifications.js:
  -> Push notification batching recognizes teacher upload events.

However, there is currently NO teacher registration endpoint, NO pre-provisioning
system, NO teacher onboarding wizard, and NO relational subject assignment table.
Past test records (e.g. 'TEACHER_1791185061104', 'TEACHER_SHARMA') were inserted
manually in test fixtures and migration scripts.

3. CAN TEACHERS SAFELY LIVE IN THE EXISTING "STUDENTS" TABLE?
================================================================================
Audit of students table:
- Over 15 existing database tables maintain foreign keys to students(studentId):
  * files.uploadedBy -> students(studentId)
  * assignments.createdBy -> students(studentId)
  * posts.user_id -> students(studentId)
  * chat_messages.studentId -> students(studentId)
  * notifications.actor_id -> students(studentId)
  * notifications.recipientStudentId -> students(studentId)
  * submission_grades.gradedBy -> students(studentId)
  * mobile_tokens.studentId -> students(studentId)
  * cohort_semester_history.promoted_by -> students(studentId)

- Architectural Problem if teachers only live in students table:
  1. students table has columns:
     semester TEXT DEFAULT 'Semester 1'
     department TEXT DEFAULT 'BIT'
     cohort_id TEXT REFERENCES cohorts(id)
  2. Front-end components (ProfileView.tsx, SearchOverlay.tsx) render:
     @{student.studentId} • {student.semester || 'Semester 1'}
  3. Defaulting a teacher to Semester 1 or a cohort breaks the academic domain model.

RECOMMENDED ARCHITECTURE: OPTION B+ (Dedicated Table + Anchor Row)
1. Introduce a dedicated teachers table storing teacher-specific domain attributes:
   id, name, username, email, designation, department, supabase_uid, status.
2. Maintain an anchor row in students:
   - studentId = teachers.id (e.g. 'tea_' + UUID)
   - role = 'teacher'
   - semester = NULL (explicitly NULL, never default 'Semester 1')
   - cohort_id = NULL (explicitly NULL, staff has cross-cohort oversight)
   - department = 'Faculty'
   - verification_status = 'verified'
3. Benefits:
   - 100% backward-compatible with all 15+ database foreign keys.
   - Zero large-scale database refactoring required.
   - Teachers are completely independent of student academic progression.

5. RECOMMENDED DATABASE SCHEMAS
================================================================================

1. teacher_invites (Provisioning & Temporary Access):
   CREATE TABLE IF NOT EXISTS teacher_invites (
     id TEXT PRIMARY KEY,
     initial_username TEXT NOT NULL UNIQUE,
     temporary_password_hash TEXT NOT NULL,
     status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'onboarding', 'completed', 'expired', 'disabled')),
     expires_at TIMESTAMPTZ NOT NULL,
     claimed_at TIMESTAMPTZ,
     created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
     created_by TEXT REFERENCES students(studentId)
   );
   CREATE INDEX IF NOT EXISTS idx_teacher_invites_status ON teacher_invites(status);
   CREATE UNIQUE INDEX IF NOT EXISTS idx_teacher_invites_username ON teacher_invites(LOWER(initial_username));

2. subjects (Canonical Course Catalog):
   CREATE TABLE IF NOT EXISTS subjects (
     id TEXT PRIMARY KEY,                       -- e.g. 'CIT111'
     code TEXT NOT NULL UNIQUE,                 -- e.g. 'CIT111'
     name TEXT NOT NULL,                        -- e.g. 'Computer Programming I (C)'
     semester INTEGER NOT NULL CHECK (semester BETWEEN 1 AND 8),
     department TEXT NOT NULL DEFAULT 'BIT',
     credit_hours NUMERIC(3, 1) DEFAULT 3.0,
     nature TEXT DEFAULT 'TH + PR',
     active BOOLEAN NOT NULL DEFAULT TRUE,
     created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
     updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
   );
   CREATE INDEX IF NOT EXISTS idx_subjects_semester ON subjects(semester);
   CREATE INDEX IF NOT EXISTS idx_subjects_code ON subjects(code);

3. teachers (Permanent Teacher Profiles):
   CREATE TABLE IF NOT EXISTS teachers (
     id TEXT PRIMARY KEY,                       -- e.g. 'tea_' + UUID
     user_id TEXT NOT NULL UNIQUE REFERENCES students(studentId) ON DELETE CASCADE,
     name TEXT NOT NULL,
     username TEXT NOT NULL UNIQUE,
     email TEXT NOT NULL UNIQUE,
     designation TEXT DEFAULT 'Instructor',
     department TEXT DEFAULT 'Faculty',
     supabase_uid TEXT UNIQUE,
     status TEXT NOT NULL DEFAULT 'active' CHECK (status IN ('active', 'disabled')),
     created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
     updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
   );
   CREATE UNIQUE INDEX IF NOT EXISTS idx_teachers_username_lower ON teachers(LOWER(username));
   CREATE UNIQUE INDEX IF NOT EXISTS idx_teachers_email_lower ON teachers(LOWER(email));

4. teacher_subjects (Teacher Capabilities - Many to Many):
   CREATE TABLE IF NOT EXISTS teacher_subjects (
     id TEXT PRIMARY KEY,
     teacher_id TEXT NOT NULL REFERENCES teachers(id) ON DELETE CASCADE,
     subject_id TEXT NOT NULL REFERENCES subjects(id) ON DELETE CASCADE,
     created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
     UNIQUE(teacher_id, subject_id)
   );
   CREATE INDEX IF NOT EXISTS idx_teacher_subjects_teacher ON teacher_subjects(teacher_id);
   CREATE INDEX IF NOT EXISTS idx_teacher_subjects_subject ON teacher_subjects(subject_id);

5. Future Table Compatibility: teacher_assignments
   Will connect teacher_id + subject_id + cohort_id + academic_year without schema breaking.

6. TEACHER ACCOUNT LIFECYCLE STATE MACHINE
================================================================================
States:
1. PROVISIONED:
   Created by admin via script with temporary credentials. Expires in 14 days.
2. ONBOARDING:
   Teacher logs in with temporary credentials. Server issues restricted onboarding token.
   Standard app APIs are blocked.
3. AWAITING_EMAIL_VERIFICATION:
   Teacher submits Full Name, New Username, Recovery Email, Permanent Password, and
   selects Subjects. Supabase user is created with email confirmation required.
   Temporary credentials marked 'completed' and invalidated.
4. ACTIVE:
   Teacher clicks verification link in email. Supabase sets email_confirmed_at.
   Teacher logs in normally using new username/email and permanent password.
5. DISABLED:
   Admin suspends account. Tokens revoked.
6. EXPIRED:
   Provisional credential not redeemed within 14 days. Admin re-issuance required.

7. RESTRICTED ONBOARDING SESSION & FIRST-LOGIN ENFORCEMENT
================================================================================
1. Temporary Login Response:
   When provisional credentials match in teacher_invites:
   - Server returns:
     {
       "onboardingRequired": true,
       "onboardingToken": "<signed_hmac_token_2h_expiry>",
       "initialUsername": "teacher001"
     }
   - NO Supabase session JWT or mobile bearer token is issued.

2. Access Boundary:
   - onboardingToken is ONLY valid for:
     GET  /api/teacher/onboarding/state
     GET  /api/subjects
     POST /api/teacher/onboarding/check-username
     POST /api/teacher/onboarding/complete
   - Normal endpoints (/api/me, /api/chat, /api/posts, /api/files) strictly reject
     the onboarding token with 401 Unauthorized / 403 Forbidden.

3. Server-Side Enforcement:
   - Teacher cannot bypass onboarding by navigating to protected URLs.
   - Client UI presents non-dismissible setup wizard.

8. IDENTITY & CREDENTIAL RULES
================================================================================
1. Full Name:
   - Required, length 2 to 100 characters.
   - Preserves honorific titles (e.g. "Dr. Ram Sharma", "Prof. A. K. Joshi").
2. Username:
   - Required, length 3 to 30 characters: ^[a-zA-Z0-9_.]{3,30}$
   - Lowercase normalized.
   - Case-insensitive unique across students and teachers.
   - Reserved usernames blacklist enforced.
3. Recovery Email:
   - Required, lowercase normalized, globally unique.
   - Mandatory email verification via Supabase Auth before account becomes ACTIVE.
4. Permanent Password:
   - Minimum 8 characters.
   - Managed entirely by Supabase Auth (same standard as students).
   - Never stored or hashed in PostgreSQL.

11. SECURITY & THREAT AUDIT
================================================================================
- Temporary Credential Theft: 14-day expiry, bcrypt hashing, rate limiting, instant
  destruction upon completion.
- Username Enumeration: Constant-time delays (60-100ms) on failed logins, generic
  error messages, enumeration-resistant password reset.
- Onboarding Bypass: Backend blocks all standard routes for onboarding tokens;
  account requires verified Supabase email.
- Privilege Escalation: Role is hardcoded to 'teacher' on the server; requireAdmin
  strictly restricts admin endpoints.
- Subject Tampering: Selected subject IDs are validated against foreign keys in
  the canonical subjects table.
- Replay Attacks: Completed invites have their password hash wiped and status set
  to 'completed'.
