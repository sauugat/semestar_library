1. EXECUTIVE SUMMARY, MISSION & CORE PURPOSE
================================================================================
Semester Library is a full-stack, enterprise-grade academic platform built from 
the ground up for Gandaki University students in the Faculty of Science & 
Technology, primarily studying the Bachelor of Information Technology (BIT) 
curriculum.

In traditional university environments, educational materials and communication 
channels are deeply fragmented:
1. Syllabus documents are distributed as scanned or unformatted PDF files where 
   students cannot quickly search credit hours, practical ratios, or unit lists.
2. Lecture notes, handwritten summaries, and PowerPoint presentations are 
   scattered across informal messaging groups (WhatsApp, Messenger, Viber, Telegram), 
   where links break and files disappear after a few months.
3. Official examination routines are photographed from physical noticeboards and 
   shared as compressed images, making it difficult for students to track exam 
   dates, room allocations, or time countdowns.
4. Computer science and programming students lack dedicated browser-based 
   environments to write, compile, debug, and submit coding lab assignments 
   tailored specifically to their university coursework.
5. Students studying after hours lack immediate, contextual academic support that 
   actually understands their university's syllabus, course units, and faculty 
   announcements.

Semester Library resolves all of these challenges within a single, integrated, 
high-performance web portal:
- Curated Academic Library: Verified, semester-segregated lecture notes, slides, 
  and previous exam questions with in-browser previewing (PDF, Word, PPTX) and 
  download counters.
- Interactive Syllabus Explorer: Complete interactive breakdown of all 8 semesters 
  of Gandaki University's BIT program, outlining course codes, credit hours, 
  objectives, unit topics, and reference books.
- Smart Exam Routine System: Live examination timetables featuring automated exam 
  time countdowns, dual calendar support (Bikram Sambat BS & Gregorian AD), 
  room assignments, and printable views.
- Code Lab IDE & Automated Grading: A browser-based programming laboratory powered 
  by Microsoft Monaco Editor (the core editor of VS Code), cloud compiler runners 
  (C, C++, Java, Python), automated testing against hidden test cases, lab report 
  PDF generation, and keystroke timelapse verification.
- Campus Social Feed & Direct Messaging: An academic social platform where students 
  and faculty publish notices, discuss questions, share code snippets, react, 
  and message each other privately in real time.
- Real-Time Cohort Group Chat: Semester-specific peer chat channels equipped with 
  rich media attachments, user mentions (@username), emoji reactions, pinned 
  teacher announcements, and online presence tracking.
- Kyana AI 3.0 (Semester AI): A specialized academic artificial intelligence 
  assistant built on Google Gemini 3.1 Flash Lite. Kyana is strictly grounded 
  in Gandaki University's curriculum and uses autonomous tool calling to search 
  uploaded lecture notes, check syllabus contents, retrieve exam routines, and 
  debug student code with zero hallucinations.
- Role-Based Governance: Dedicated dashboards for Administrators and Faculty 
  Members to manage academic cohorts, assign courses, evaluate programming lab 
  submissions, grade work, and moderate content.

3. FRONTEND ARCHITECTURE — DETAILED CLIENT IMPLEMENTATION

A. THE PHILOSOPHY OF VANILLA WEB TECHNOLOGIES (HTML5 / CSS3 / ES6+)
In modern web development, teams frequently default to heavy frontend frameworks 
(React, Next.js, Vue, Angular). Semester Library deliberately took a different 
engineering path by building the entire web client using pure Semantic HTML5, 
Vanilla CSS3, and Modern ES6+ JavaScript.

Key Advantages:
1. Instant Page Loads: Browser receives clean HTML, CSS, and JS directly over the 
   wire. There is no multi-megabyte JavaScript bundle to download, parse, and 
   hydrate before the page becomes interactive. First Contentful Paint (FCP) is 
   consistently achieved under 150ms.
2. Complete Freedom from Build Pipelines: There is no Webpack, Vite, or Babel 
   compilation step required for the frontend. You can modify any HTML or JS 
   file, save it, and refresh your browser immediately to see changes.
3. Fine-Grained DOM Control: Components attach event listeners directly to 
   standard DOM elements, avoiding the memory overhead of virtual DOM diffing.
4. Longevity & Low Maintenance: Native web standards do not suffer from breaking 
   framework version upgrades (e.g., React 17 -> 18 -> 19 breaking changes).

B. DESIGN SYSTEM, TYPOGRAPHY, LAYOUT & AESTHETIC POLISH
The design system is implemented in `public/style.v4.css` and `public/theme-overrides.css`, 
drawing visual inspiration from Apple Human Interface Guidelines, Linear.app, and Vercel:
- Dark-Mode First Palette: Built on neutral, high-contrast dark tones:
  * Primary Canvas: #0a0a0a
  * Card Surfaces: #141414 and #1c1c1c
  * Raised Dialogs & Modals: #222222
  * Subtle Glass Borders: rgba(255, 255, 255, 0.08)
  * Text Contrast: Primary text is crisp white (#f5f5f7), secondary text is 
    subtle slate (#a1a1a6), and tertiary labels are muted (#71717a).
- Glassmorphism & Depth:
  Top navigation bars, modal backdrops, and floating action toolbars use 
  `backdrop-filter: blur(16px) -webkit-backdrop-filter: blur(16px)` combined with 
  semi-transparent surface colors (`background: rgba(18, 18, 18, 0.75)`).
- Typography System (Google Fonts):
  * Plus Jakarta Sans & Outfit: Geometric, modern sans-serif fonts used for brand 
    headings, page titles, and prominent statistics.
  * Inter: Engineered for maximum legibility in body paragraphs, user comments, 
    and UI tables.
  * Fira Code & JetBrains Mono: Monospaced typography with programming ligatures 
    used inside the Monaco code editor, compiler terminal outputs, and syllabus 
    course codes.
- Bento Grid Layout:
  The homepage (`public/index.html`) organizes platform modules (Routine, Syllabus, 
  Notes Library, Compiler, Community) into an asymmetrical Bento grid inspired by 
  Apple promotional showcases. Cards feature subtle hover transforms, radial 
  border gradients, and responsive auto-fitting grid tracks.

C. THE ANTI-FOUC THEME ENGINE (theme.js & theme-overrides.css)
A major challenge in dark-themed web applications is FOUC (Flash of Unstyled 
Content) — where a white page briefly flashes on screen before the user's saved 
theme preference is applied.
Semester Library eliminates FOUC through `public/theme.js`:
1. `theme.js` is placed directly inside the `<head>` tag of every HTML page as 
   an inline, synchronous script BEFORE any stylesheet or `<body>` element.
2. It executes synchronously before the browser paints the very first pixel:
   ```javascript
   (function() {
     const savedTheme = localStorage.getItem('theme');
     const systemDark = window.matchMedia('(prefers-color-scheme: dark)').matches;
     if (savedTheme === 'dark' || (!savedTheme && systemDark)) {
       document.documentElement.classList.add('dark');
     } else {
       document.documentElement.classList.remove('dark');
     }
   })();
   ```
3. Because the `.dark` class is applied to `document.documentElement` (`<html>`) 
   instantly, the CSS immediately applies the dark background color, ensuring 
   zero white flash.
4. When the user toggles the theme switch button, `theme.js` toggles `.dark` and 
   updates `localStorage.setItem('theme', newTheme)`.

D. CLIENT-SIDE STATE MANAGEMENT WITHOUT FRAMEWORKS
Without a heavy framework like Redux or Zustand, state is managed through 
disciplined vanilla patterns:
1. URL Search Parameters: Filtering state (such as `?semester=2&subject=Data+Structures`) 
   is written directly to `window.location.search`. This makes every view directly 
   shareable and bookmarkable, and preserves filter state across page reloads.
2. Dataset Attributes: DOM elements store entity IDs directly in HTML5 data 
   attributes (e.g., `<button data-post-id="42" data-liked="true">`). Event 
   delegation listeners on parent containers read `event.target.dataset.postId` 
   without re-rendering lists.
3. Session and Local Storage Caches:
   * `localStorage`: Stores persistent user preferences (theme preference, 
     Supabase session tokens, Code Lab draft code).
   * `sessionStorage`: Stores ephemeral data (academic context cache, active 
     filters, chat scroll positions) that reset when the tab closes.

E. UNIVERSAL AUTHENTICATED FETCH LAYER (auth.js & authFetch)
In `public/auth.js`, the platform defines `authFetch(url, options)`, which wraps 
the standard browser `fetch`:
1. Token Injection: Checks if an active Supabase session exists in memory or 
   `localStorage`. If found, it automatically attaches:
   `headers['Authorization'] = 'Bearer ' + token;`
2. Auto-Refresh on Expiry: If a protected backend API endpoint responds with 
   `401 Unauthorized`:
   - `authFetch` intercepts the response.
   - It calls `supabase.auth.refreshSession()` to exchange the refresh token for a 
     fresh access token.
   - If the refresh succeeds, it updates the stored token, re-attaches the new 
     header, and replays the original failed request seamlessly without the user 
     noticing any disruption.
   - If the refresh fails (session truly revoked), it clears stored credentials 
     and routes the user to `/login.html`.

F. IN-BROWSER DOCUMENT RENDERING ENGINES
Students can preview study materials directly in their browser without downloading:
1. PDF Rendering with PDF.js (`pdfjs-dist`):
   When a student clicks "View Note", `public/library.html` initializes a canvas-based 
   PDF viewer. It downloads the document stream, renders PDF pages onto an 
   HTML5 `<canvas>` element with pinch-to-zoom, page navigation, and text 
   selection support.
2. Microsoft Word Rendering with Mammoth.js:
   For `.docx` lecture files, `mammoth.convertToHtml({ arrayBuffer })` converts 
   Word document formatting, headings, bullet lists, and tables into clean semantic 
   HTML that renders natively inside the modal container.
3. PowerPoint Presentation Previews:
   Handled via server-side preview extraction (`lib/office-preview.js`) and slide 
   carousel navigation.

G. CODE LAB MONACO IDE INTEGRATION & KEYBOARD BINDINGS
Inside `public/code-lab/index.html` and `public/code-lab/assignment.html`:
1. Monaco Editor (the engine powering Microsoft Visual Studio Code) is loaded 
   dynamically via AMD loader (`vs/loader.js`).
2. Provides full syntax highlighting, bracket pair colorization, line numbering, 
   code folding, and auto-indentation for C, C++, Java, and Python.
3. Custom Keyboard Shortcuts:
   * `Ctrl+Enter` or `Cmd+Enter`: Compiles and runs code against standard input.
   * `Ctrl+S` or `Cmd+S`: Saves code draft locally in `localStorage`.
   * `F11`: Toggles distraction-free fullscreen coding mode.

H. PROGRESSIVE WEB APP (PWA) OFFLINE ENGINE (sw.js & manifest.json)
The website is fully configured as an installable Progressive Web App (PWA):
1. `public/manifest.json`: Defines the application name ("Semester Library"), 
   display mode (`standalone`), start URL, brand colors (#0a0a0a), and high-resolution 
   home screen icons.
2. Service Worker (`public/sw.js`):
   - Pre-caches core application shells (`index.html`, `style.v4.css`, `theme.js`, 
     `syllabus-data.json`).
   - Implements a Stale-While-Revalidate caching strategy for syllabus and static 
     assets, allowing students to access syllabus data even when completely offline 
     inside lecture halls.

4. AUTHENTICATION, AUTHORIZATION & SECURITY DEEP DIVE
================================================================================

A. THE THREE PLATFORM ROLES & PRIVILEGES
Semester Library implements strict Role-Based Access Control (RBAC):
1. Role: `student`
   - Target: Enrolled Gandaki University students.
   - Permissions: Browse library notes, download study materials, inspect syllabus 
     and routines, upload lecture notes, create community posts, write comments, 
     participate in cohort chat, send 1-on-1 direct messages, and solve Code Lab 
     assignments.
   - Enrollment: Auto-assigned to an active Academic Cohort matching their semester 
     (e.g., BIT 2024-2028).
2. Role: `teacher`
   - Target: Faculty instructors and professors.
   - Permissions: All student privileges plus: create programming assignments, 
     define test cases, inspect student code submissions, run automated evaluation 
     against hidden test cases, grade lab reports, enter marks, write feedback, 
     publish official teacher notices, and pin announcements in cohort chat.
   - Enrollment: Provisioned strictly by administrators via invite codes; cannot 
     self-register.
3. Role: `admin`
   - Target: Platform system administrators and university department heads.
   - Permissions: Full administrative authority: view system metrics, promote 
     academic cohorts from one semester to the next, archive graduated cohorts, 
     provision teacher invites, manage subject assignments, suspend/reactivate 
     accounts, demote or promote roles, and moderate or delete inappropriate content.

B. TRI-CHANNEL AUTHENTICATION ARCHITECTURE
The system unifies three complementary authentication mechanisms:

1. Channel 1: Supabase Auth JWTs (Primary Client API Token)
   - Utilized by modern web clients and mobile clients.
   - Supabase generates signed JSON Web Tokens (RS256/HS256) containing `sub` 
     (Supabase UID), `email`, and expiration timestamps.
   - The backend validates the signature against Supabase public keys via 
     `verifySupabaseToken(token)` in `lib/supabase.js`.
   - The student record is then matched in Neon PostgreSQL by `supabase_uid` or 
     `email`.

2. Channel 2: Express Session Cookies (Persistent Web Session)
   - Browser web requests carry a secure HTTP-only cookie named `__gu_session`.
   - Cookie Flags: `httpOnly: true`, `sameSite: 'lax'`, `secure: true` in production, 
     `maxAge: 7 days`.
   - Stored in the Neon PostgreSQL `session` table via `CustomDbStore` in `server.js`.
   - Survives serverless function container cold starts and server restarts.

3. Channel 3: Mobile Persistent Bearer Tokens
   - Stored in the `mobile_tokens` table (`token`, `studentId`, `createdAt`, `expiresAt`).
   - Uses a 64-character hexadecimal cryptographically secure random token.
   - Validated in `lib/auth-middleware.js` using an optimized single-query SQL join:
     ```sql
     SELECT m.token, m.studentId, m.expiresAt, s.name, s.role, s.semester, s.cohort_id
     FROM mobile_tokens m
     LEFT JOIN students s ON s.studentId = m.studentId
     WHERE m.token = ?
     ```

C. STEP-BY-STEP AUTHENTICATION LIFECYCLES

Workflow 1: Student Self-Registration & Real-Time Availability Checking
1. Student navigates to `/register.html`.
2. As the student types their desired username or email, an input debounce timer 
   calls `POST /api/auth/check-availability` with `{ username, email }`.
3. Backend checks uniqueness across the `students` table and returns `{ available: true }` 
   or `{ available: false, message: 'Username is already taken' }`.
4. Client provides live visual feedback (green checkmark or red warning) before 
   submission.

Workflow 2: Supabase Email OTP Verification & Cohort Auto-Assignment
1. Student enters full registration data and submits form.
2. Client initiates Supabase email signup with 6-digit OTP confirmation.
3. Supabase sends a verification code to the student's email address.
4. Student enters the 6-digit OTP; upon verification, Supabase returns a verified 
   access token.
5. Client calls `POST /api/auth/register` (or `/api/auth/finalize-signup`) with 
   the verified token and profile information.
6. Backend Security & Execution:
   - Validates that `authUser.email_confirmed_at` is present.
   - Enforces privilege escalation defense: strictly overrides any user-supplied 
     role to `'student'` and sets `verification_status = 'verified'`.
   - Resolves the active academic cohort: checks which active cohort in the `cohorts` 
     table matches the chosen semester (e.g., Semester 2 -> Cohort BIT 2024-2028).
   - Inserts record into `students` table.
   - Logs cohort audit trail (`signup_auto_assign`).
   - Generates mobile bearer token and initializes Express session.

Workflow 3: Standard Password Login & Session Fixation Defense
1. User enters identifier (Student ID, Username, or Email) and password at `/login.html`.
2. Request hits `POST /api/login` (protected by `loginRateLimiter`).
3. Backend looks up student record in database.
4. If account status is `suspended`, backend rejects request with 403 `ACCOUNT_SUSPENDED`.
5. Compares submitted password against `students.passwordHash` using `bcrypt.compareSync()`.
6. Session Fixation Defense:
   - Calling `req.session.regenerate()` discards the existing anonymous session ID 
     and issues a completely new session identifier.
   - Prevents attackers from harvesting unauthenticated session cookies and 
     hijacking user sessions after login.
7. Role-Based Destination Routing:
   - Admin -> Redirects to `/admin-dashboard.html`
   - Teacher -> Redirects to `/teacher-dashboard.html`
   - Student -> Redirects to `/dashboard.html`

Workflow 4: Teacher Provisioning, Nonce Tracking & Self-Onboarding
To protect academic integrity, teachers cannot freely register as faculty:
1. Administrator accesses `/admin-teachers.html`, enters the instructor's name, 
   initial username, and assigned course subjects.
2. Server generates a unique invite record in `teacher_invites`:
   - Generates a cryptographically random temporary password.
   - Hashes temporary password via bcrypt.
   - Sets status to `'provisioned'` with an onboarding nonce (default: 1) and 
     expiration date (7 days).
3. Admin delivers temporary credentials to the instructor.
4. Instructor visits `/login.html` and enters the temporary credentials.
5. The login endpoint detects that the credentials match a `teacher_invites` record 
   and returns:
   `{ onboardingRequired: true, onboardingToken: "...", state: { initialUsername, ... } }`
6. The onboarding token is signed specifically with `{ typ: 'teacher_onboarding' }`. 
   `lib/auth-middleware.js` strictly forbids onboarding tokens from accessing 
   standard user APIs.
7. Instructor is routed to `/teacher-onboarding.html`:
   - Instructor chooses a new permanent password and enters their official faculty email.
   - Verifies email via OTP.
   - System promotes account to `role = 'teacher'`, links records in `teachers` 
     and `teacher_subjects`, and marks the invite as `'completed'`.

Workflow 5: Account Suspension Checks & Security Interceptors
1. Administrators can suspend disruptive accounts from `/admin-dashboard.html`.
2. When an account is suspended, `students.account_status` is updated to `'suspended'`.
3. In `lib/auth-middleware.js`, every incoming request verifies `account_status`:
   - If suspended, `req.isSuspended = true`.
   - Any access to protected routes returns HTTP 403:
     ```json
     {
       "error": "ACCOUNT_SUSPENDED",
       "code": "ACCOUNT_SUSPENDED",
       "message": "Your account has been suspended by an administrator. Please contact support."
     }
     ```
   - If authenticated via mobile token, the token is immediately purged from 
     `mobile_tokens`.

5. BACKEND ARCHITECTURE & PROCESSING ENGINES
================================================================================

A. THE EXPRESS 4 SERVER KERNEL (server.js) & SERVERLESS ADAPTER
`server.js` serves as the central orchestration kernel for the entire application:
- Async Error Handler Monkey-Patch:
  Express 4 historically required manual `try/catch` blocks inside async route 
  handlers. `server.js` monkey-patches `Layer.prototype.handle_request` so any 
  unhandled promise rejection in an async route is automatically caught and 
  forwarded to `next(err)`, preventing server crashes.
- Serverless Execution on Vercel:
  * In local development, `server.js` starts a persistent HTTP server listening 
    on port 3000 (`app.listen(PORT)`).
  * On Vercel, `api/index.js` exports `app` directly as a Serverless Function.
  * In `vercel.json`, all routes (`/(.*)`) are rewritten to `/api/index.js`.
  * Temporary file uploads automatically switch from local `./uploads` to `/tmp/uploads` 
    when running inside read-only AWS Lambda / Vercel container environments.
- Rate Limiting Policies (`express-rate-limit`):
  * `loginRateLimiter`: 5 failed attempts per 15-minute window on auth endpoints.
  * `submitLimiter`: Max 10 assignment submissions per minute on Code Lab.
  * `explainLimiter`: Max 10 AI code explanation requests per minute.
  * `eventsLimiter`: Rate limits Code Lab competition event submissions.

B. DUAL-ENGINE UNIVERSAL DATABASE ABSTRACTION (db.js)
`db.js` provides an abstraction layer that allows the entire application to run 
identically on Neon PostgreSQL (production) or SQLite/LibSQL (development and testing):
1. Connection Management:
   - PostgreSQL / Neon: Uses `@neondatabase/serverless` with a `Pool` configured 
     with WebSocket constructor (`neonConfig.webSocketConstructor = ws`). Handles 
     idle client terminations and automatic reconnections.
   - SQLite / LibSQL: Uses `@libsql/client` pointing to `database.db` with 
     Write-Ahead Logging (`PRAGMA journal_mode = WAL`) and a 5000ms busy timeout.
2. Dynamic Query Dialect Translation (`toPostgresSql`):
   When the app runs on PostgreSQL, `db.js` automatically rewrites queries on the fly:
   * Replaces SQLite positional parameter `?` with PostgreSQL numbered parameters 
     `$1, $2, $3, ...`.
   * Replaces SQLite timestamp functions `datetime('now')` with PostgreSQL 
     `CURRENT_TIMESTAMP`.
3. Column Normalization Engine (`camelMap`):
   PostgreSQL converts all unquoted column names to lowercase (e.g., `studentId` 
   becomes `studentid`).
   `db.js` intercepts all query results and maps lowercase keys back into camelCase 
   JavaScript properties using a comprehensive lookup map (`studentid` -> `studentId`, 
   `passwordhash` -> `passwordHash`, `avatarurl` -> `avatarUrl`, `createdat` -> `createdAt`).

C. 3-TIER OBJECT & BINARY STORAGE ENGINE
Files uploaded to Semester Library (notes, slides, post images, avatars) use a 
three-tier persistence model:
1. Tier 1 (Cloud Object Storage):
   Files are uploaded to Supabase Cloud Storage buckets (`library_files` and `posts`) 
   via `lib/supabase.js`. Produces global CDN URLs for high-speed streaming.
2. Tier 2 (Database Blob Persistence):
   If cloud object storage is unavailable or operating in offline testing mode, 
   `db.storeFileBlob(filename, buffer, mimeType)` saves binary files directly into 
   the `file_blobs` database table.
3. Tier 3 (Serverless Local Disk Cache):
   When a serverless Lambda instance spins up, local `/tmp/uploads` is empty. The 
   function `ensureLocalFile(filename)` in `server.js` checks if the file exists on 
   disk. If missing, it fetches the binary from the `file_blobs` table, writes it 
   to `/tmp/uploads`, and serves it immediately.

D. FULL-TEXT DOCUMENT INGESTION & SEARCH ENGINE (lib/note-search.js)
Whenever an academic file is uploaded, the background indexing pipeline executes:
1. Text Extraction:
   - PDF: `pdfjs-dist` loads document pages sequentially and extracts text blocks.
   - Word (.docx): `mammoth.extractRawText()` parses XML document streams.
   - PowerPoint (.pptx): `node-pptx-parser` extracts slide titles and speaker notes.
2. Search Vector Generation:
   - In PostgreSQL: Converts extracted text into a search vector using 
     `to_tsvector('english', content)`.
   - Stored in the `note_search_documents` table with a Generalized Inverted Index (GIN).
   - In SQLite: Extracted text is inserted into an `FTS5` virtual table with Porter 
     stemming.
3. Query Execution:
   Searching `/api/search?q=algorithms` executes a weighted full-text search 
   matching titles, chapters, and body paragraphs, returning ranked results in 
   under 10 milliseconds.

E. KYANA AI 3.0 ACADEMIC ASSISTANT
Kyana AI is the built-in academic intelligence engine:
1. LLM Core:
   Connects to Google Gemini 3.1 Flash Lite via direct streaming HTTP calls in 
   `lib/chat-provider.js` (with OpenRouter as an automatic fallback).
2. Grounded Autonomous Tool Calling (`lib/chat-tools.js`):
   Before replying to student questions, Kyana inspects the query and can call:
   * `search_notes`: Queries lecture notes and extracted slide text.
   * `get_syllabus`: Looks up exact BIT course outlines and textbook references.
   * `get_routine`: Retrieves upcoming exam dates, times, and room numbers.
   * `web_search`: Retrieves current external technical documentation.
3. Authority Ranking Tiers (`lib/knowledge-*.js`):
   When synthesizing information from the campus feed, Kyana weights sources by 
   academic authority:
   * Tier 1 (Highest): Official University Notices
   * Tier 2: Faculty Assignments & Teacher Announcements
   * Tier 3: Class Representative (CR) Announcements
   * Tier 4: Student Community Posts
4. Bilingual Streaming:
   Kyana fluently understands and responds in both English and Nepali (including 
   Romanized Nepali like "exam routine kahile auncha?"). Responses stream token-by-token 
   over Server-Sent Events (SSE).

F. REAL-TIME MESSAGING ENGINES
Real-time features operate over two resilient channels:
1. Supabase Realtime Channels (Cohort Chat & DM):
   - Group chat rooms and 1-on-1 direct messages broadcast payloads over Supabase 
     Realtime WebSocket channels (`public:chat_messages` and `dm_realtime_outbox`).
   - Connected browser clients receive incoming messages instantly without polling.
2. Interactive WebSocket Terminal (`ws`):
   - At `/api/compiler/live`, a native WebSocket server spawns interactive terminal 
     sessions for running student code with live bidirectional stdin/stdout.

G. CODE LAB CLOUD COMPILER & AUTOMATED GRADING
Code Lab allows students to test code and complete assignments:
1. Remote Code Execution:
   `routes/code-lab/run.js` formats code payloads and sends them to the Paiza.io 
   compiler API. Tracks execution time, memory usage, and captures compiler errors.
2. Automated Test Case Runner:
   When an assignment is submitted, `routes/code-lab/assignments.js` iterates through 
   all test cases defined for that problem:
   - Feeds `test_case.input` into the program.
   - Compares actual output against `test_case.expected_output` (ignoring trailing whitespace).
   - Evaluates hidden test cases to prevent students from hardcoding output strings.
   - Calculates the final percentage score and records the submission in `submissions`.
3. Anti-Plagiarism Keystroke Playback:
   `timelapse.html` captures keystroke intervals during coding and allows teachers 
   to replay the student's typing progression to verify authentic student work.

H. MULTI-CHANNEL NOTIFICATION ENGINE
Notifications keep students updated on campus life:
1. In-App Notification Center (`routes/notifications.js`):
   Records user notifications in the `notifications` table for post likes, comments, 
   mentions, uploaded notes, and new assignments.
2. Mobile Expo Push Service (`lib/push-notifications.js`):
   Queues push notifications in `push_notification_outbox`, batches transmissions 
   to the Expo Push API, tracks delivery receipts, and handles automatic retries.

================================================================================
9. END-TO-END DATA FLOWS & TRANSACTION WALKTHROUGHS
================================================================================

Flow A: Student Registration & Cohort Allocation
1. Student fills out form at `/register.html`.
2. Supabase verifies student's email address via a 6-digit confirmation OTP.
3. Client receives verified access token and calls `POST /api/auth/register`.
4. Backend `server.js` validates token with Supabase and checks that email is confirmed.
5. Resolves active cohort: queries `cohorts` table for the active batch matching 
   the student's selected semester (e.g., Semester 2 -> Cohort BIT 2024-2028).
6. Inserts user into `students` table in Neon PostgreSQL with `role = 'student'` and 
   `verification_status = 'verified'`.
7. Records audit entry in `cohort_audit_logs`.
8. Generates mobile bearer token, initializes session, and returns redirect to 
   `/dashboard.html`.

Flow B: Lecture Note Upload, Extraction, Indexing & Preview
1. Student logs in and navigates to `/files.html`.
2. Student selects PDF file, selects subject ("Database Management Systems"), 
   semester ("Semester 3"), and chapter ("Unit 2: Normalization").
3. Client submits multipart form request to `POST /api/files/upload`.
4. `auth-middleware.js` validates JWT, verifies account is active, and attaches `req.user`.
5. `multer` writes file to disk cache and computes unique hash name.
6. `lib/supabase.js` streams file to Supabase Cloud Storage bucket (`library_files`).
7. Metadata is stored in `files` table in Neon PostgreSQL.
8. Background Indexing:
   - `lib/note-search.js` extracts raw text from PDF using `pdfjs-dist`.
   - Text is converted to a `TSVECTOR` and stored in `note_search_documents` with 
     a GIN index.
   - Kyana AI knowledge cache is invalidated so the new note is immediately searchable.
9. Student visits `/library.html`, clicks "Preview Note":
   - PDF.js downloads binary stream and renders pages onto an HTML5 canvas directly 
     inside the modal.

Flow C: Kyana AI Question Answering with Tool Execution
1. Student types in `/chatbot.html`: "When is our DBMS final exam and what are the units?"
2. Client sends request to `POST /api/chat/ai` with `stream: true`.
3. `server.js` routes request to `ai-assistant.js`:
   - `chat-mode.js` identifies dual intent: exam routine inquiry and syllabus inquiry.
   - Model determines it needs authoritative facts and triggers tool calls:
     * Tool 1: `get_routine({ subject: "DBMS", semester: 3 })` queries `routine` table.
     * Tool 2: `get_syllabus({ subject: "Database Management Systems", semester: 3 })` 
       queries `syllabus-data.json`.
4. Tools execute and return structured data to the model.
5. `chat-provider.js` calls Google Gemini 3.1 Flash Lite with the system personality, 
   student question, and tool results.
6. Gemini generates a comprehensive, factual answer and streams text chunks back over SSE.
7. `chatbot.js` renders markdown on screen, displays math formulas via KaTeX, and 
   renders two interactive UI citation cards:
   - Card 1: Exam Routine card showing date, time, and room number.
   - Card 2: Syllabus card showing course units and credit hours.

Flow D: Code Lab Assignment Submission & Automated Evaluation
1. Student opens `/code-lab/assignment.html?id=5`.
2. Problem statement and starter template load into Monaco Editor.
3. Student writes C code and clicks "Run Code":
   - Code is sent to `POST /api/code-lab/run`.
   - Code executes against standard input via Paiza.io API; output appears in console.
4. Student clicks "Submit Assignment":
   - Code is sent to `POST /api/code-lab/submit`.
   - Backend queries all test cases for Question 5 from `question_test_cases`.
   - Executes student code against visible test cases and hidden test cases.
   - Calculates percentage score (e.g., 5/5 test cases passed = 100%).
   - Stores submission in `submissions` table along with keystroke timelapse data.
5. Teacher opens `/code-lab/submissions.html`:
   - Reviews student submission, inspects test case execution diffs, verifies 
     typing timelapse, enters marks, and submits remarks.
   - Status updates in `submission_grades`.

Flow E: Direct Messaging with Real-Time Broadcast & Read Receipts
1. Student A opens `/dashboard.html` or DM drawer and selects Classmate B.
2. Client calls `GET /api/dm/conversations/:id/messages` to load message history.
3. Student A types a message and clicks Send.
4. Client sends request to `POST /api/dm/conversations/:id/messages`.
5. Backend verifies neither student has blocked the other.
6. Message is inserted into `dm_messages` table.
7. Message payload is broadcast via Supabase Realtime channel `dm_realtime_outbox`.
8. Classmate B's browser receives WebSocket broadcast instantly and appends message 
   bubble to screen.
9. When Classmate B views the window, client sends `POST /api/dm/conversations/:id/read`, 
   updating `is_read = true` in database and showing read receipt checkmarks to Student A.

D. PRACTICAL WALKTHROUGH: ADDING A NEW DATABASE TABLE & MIGRATION
To add a new table (e.g., `events`):
1. In `schema.sql`, add the DDL:
   ```sql
   CREATE TABLE public.events (
       id SERIAL PRIMARY KEY,
       title TEXT NOT NULL,
       description TEXT,
       event_date TIMESTAMPTZ NOT NULL,
       venue TEXT,
       created_by TEXT REFERENCES students(studentid),
       created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
   );
   ```
2. In `db.js`, add the table creation query inside `initSchema()` so it automatically 
   executes on development and test SQLite instances:
   ```javascript
   await this.run(`
     CREATE TABLE IF NOT EXISTS events (
       id INTEGER PRIMARY KEY AUTOINCREMENT,
       title TEXT NOT NULL,
       description TEXT,
       event_date TEXT NOT NULL,
       venue TEXT,
       created_by TEXT,
       created_at TEXT DEFAULT CURRENT_TIMESTAMP
     )
   `);
   ```

E. PRACTICAL WALKTHROUGH: ADDING A NEW API ENDPOINT WITH VALIDATION
To create an API endpoint (e.g., `POST /api/events`):
1. In `server.js` or in a new module `routes/events.js`:
   ```javascript
   app.post('/api/events', requireLogin, async (req, res) => {
     const { title, description, eventDate, venue } = req.body || {};
     
     if (!title || !eventDate) {
       return res.status(400).json({ message: 'Title and event date are required.' });
     }
     
     try {
       const result = await db.run(
         `INSERT INTO events (title, description, event_date, venue, created_by)
          VALUES (?, ?, ?, ?, ?)`,
         title.trim(),
         description ? description.trim() : null,
         eventDate,
         venue ? venue.trim() : null,
         req.user.studentId
       );
       
       return res.status(201).json({
         success: true,
         message: 'Event created successfully',
         eventId: result.lastInsertRowid || result.id
       });
     } catch (err) {
       console.error('Failed to create event:', err);
       return res.status(500).json({ message: 'Internal server error creating event.' });
     }
   });
   ```
